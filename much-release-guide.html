Cutting an Odoo Addon Release

How to release one of our Odoo addon repositories, step by step — written for someone doing it for the very first time.

👋 Welcome — start here

This handbook walks you through releasing one of our Odoo addon repositories. If you've never done a git-based release before, don't worry — every step is spelled out, and nothing is assumed.

You should be comfortable with the basics of git (branches, commits, pushing) and have the GitHub CLI (gh) installed and logged in. Everything else you'll learn here. The examples use much-order-shopware-integration, but the process is identical for every addon repo.

🧠 The one big idea

A release is simply: bump the version number, move the tested code from the QA branch onto the Stable branch, freeze it as a version branch, and write release notes. That's it. The golden rule that keeps you safe: always ask for confirmation before any git push or anything hard to undo.

1 What a release is

Turning "tested work on the QA branch" into an official, named version our customers can install.

Each of our repos is an Odoo addon repository — a folder of modules (each module is a sub-folder with its own __manifest__.py that, among other things, declares a version). Throughout a sprint, developers open pull requests; once a PR is reviewed and tested it gets merged into the QA branch. So at any moment the QA branch holds "everything we've finished and tested but haven't shipped yet."

A release is the deliberate moment we say "this batch is good — ship it." Four things happen, and each exists for a concrete reason:

What we doWhy it's needed
Bump the version in every module's manifestOdoo decides whether to run a module's upgrade scripts by comparing the installed version to the new one. If the number doesn't change, Odoo thinks nothing changed and skips the upgrade — so customers would keep running old code.
Merge QA → Stable branchStable (X.latest) is the branch production systems actually pull from. Until code reaches Stable, no customer has it.
Create a version branchA permanent, frozen snapshot named for the exact version, so months later we can see (or re-deploy) precisely what shipped as 19.0.1.1.4 — even after Stable has moved on.
Write release notesSo the team, the client, and their Steuerberater/end-users know what changed — and support can trace a bug to the release that introduced or fixed it.

🧪 QA branch

Where tested work accumulates. A release always starts here, and it's the source of truth for "what's new."

🏷️ Version branch

A frozen, named snapshot (e.g. 19.0.1.1.4). Nobody commits to it again — it's the deliverable, kept for the record.

ℹ️

Who runs this? Usually the assistant runs it for you via the /release command, pausing to ask for your confirmation at each push. This handbook explains what that command does and why, so you understand each step — and can do it by hand if the tooling ever isn't available.

2 Branch map & vocabulary

Four names built from one number. Learn these and the rest is mechanical. (Full list in the glossary.)

Everything derives from the major version — for example 19, which is the Odoo major we build for. From that single number you can derive every branch name in the release, which is exactly why the process is so mechanical:

NameWhat it is & why it existsExample
MAJORThe Odoo major version everything is built for. Determines all three branch names below.19
QA branchWhere finished, tested work lands during the sprint. A release starts here because it's the collecting point — the newest good code lives here.19.latest-qa
Stable branchThe production-facing branch customers pull from. Kept "clean" — only released code reaches it, so it's always safe to deploy.19.latest
Version branchAn immutable snapshot named exactly for the release. Never committed to again; it's the historical record of "what shipped as this version."19.0.1.1.4
__manifest__.pyEach module's descriptor. Holds the "version" string we bump; Odoo reads it to decide whether to upgrade the module."19.0.1.1.4"

Reading the version number

Our versions follow Odoo's five-part convention MAJOR . 0 . x . y . z. Understanding the segments tells you (and the reviewer) how big a release is:

SegmentIn 19.0.1.1.4Meaning
1 — Odoo major19The Odoo version. Rarely changes within a repo's life.
2 — Odoo minor0Odoo's own minor; we keep it at 0.
3 — module major1Bumped for big/breaking changes to our module.
4 — feature1Bumped when a new feature ships.
5 — patch4Bumped for bug-fix-only releases (the most common — like this one).
💡

This is why the version is a human decision (Chapter 4), not automatic: only a person knows whether this batch is "just fixes" (bump the last digit) or "a new feature" (bump the fourth). The three fixes in our example release were all bug fixes → …1.1.3 became …1.1.4.

⚠️

Golden rule, again: ask for a clear "yes" before every push or destructive action. There are three pushes in a release (QA, Stable, version branch) — each gets its own confirmation, because each one publishes something to origin that other people and systems will pull.

3 Find what to release

Work out where you are, then list what's new since the last release.

Step 1 — Determine the context

Before touching anything, you need two facts: which branch am I on, and which major version am I releasing. Get them wrong and you could bump the wrong repo line entirely.

git branch --show-current
# → prints e.g.  19.latest-qa
  • Finding the major: it's either handed to you (e.g. you ran /release 19) or you read it off the branch name, which follows the pattern X.latest-qa — so 19.latest-qa → major 19. If neither is available (say you're on a feature branch), stop and ask rather than guessing.
  • Why the branch matters: a release must start from the QA branch, because that's the branch that holds the newest tested code. If git branch --show-current shows anything other than 19.latest-qa, ask the reviewer whether to switch (git checkout 19.latest-qa) before continuing — don't switch silently.

Step 2 — Show the commits since the last tag

Now answer "what's actually new?" The last release left behind a tag (a permanent marker on the commit that shipped). Everything committed after that tag is what this release will contain. First, find that tag:

# newest v19 tag, sorted by when it was created
git tag --list 'v19*' --sort=-creatordate | head -1
# → v19.0.1.1.3

Two flags matter here: --sort=-creatordate orders tags by creation time (the leading - means newest first) rather than alphabetically — important because v19.0.1.1.10 would sort before v19.0.1.1.9 alphabetically, giving you the wrong "latest." head -1 then keeps only the top (newest) one.

Then list the commits between that tag and where you are now (HEAD):

git log v19.0.1.1.3..HEAD --oneline --no-merges
  • v19.0.1.1.3..HEAD is a range: "everything reachable from HEAD that wasn't already in the tag" — i.e. exactly the new work.
  • --oneline prints one short line per commit (hash + subject) so it's easy to scan.
  • --no-merges hides merge commits, leaving only the real code changes — these are what you'll categorize into the release notes.

Display the result clearly (a table is ideal). Then run it again with --merges to pull out the PR numbers — merge commits carry text like "Merge pull request #97", and you'll cite those numbers in the notes:

git log v19.0.1.1.3..HEAD --merges --oneline
# → d44bb37 Merge pull request #97 from much-GmbH/56976-fix-vat-19
🛑

No new commits? Stop. If the range is empty, the last tag already points at HEAD — there is genuinely nothing to release. Tell the reviewer and end here; bumping a version with no changes would just create noise.

4 Ask for the version

The new version number is a human decision — never guessed.

Ask the reviewer plainly: "What version should this release be?" and do not proceed until they answer. This is deliberately a manual gate — see Chapter 2, only a human knows whether this batch counts as a patch, a feature, or a breaking change, and that judgement decides which digit moves.

v19.0.1.1.3 → you ask → 19.0.1.1.4

Why not just auto-increment the last digit? Because it would silently mislabel releases. A release full of new features that only bumped the patch digit would tell customers "minor fixes" when it's actually a feature drop — the version number is a promise about what changed, so a person confirms it.

⚠️

The most common beginner slip: the v prefix. The git tag carries it (v19.0.1.1.3) because tags conventionally do. The manifest version and the branch name do not (19.0.1.1.4). So when the reviewer says "make it v19.0.1.1.4", you write 19.0.1.1.4 into the manifests and name the branch 19.0.1.1.4 — the v only appears in tag-related places like the changelog URL.

5 Bump the manifests

Every module carries its own version, so every module gets bumped to the new number — together, in lockstep.

First, locate every manifest that actually declares a version. A repo can have helper folders (tests, static assets) without manifests, so we search rather than assume:

# list every manifest file that contains a "version" key
find . -name "__manifest__.py" | xargs grep -l '"version"'

Reading that command: find . -name "__manifest__.py" walks the whole repo and prints every manifest path; the pipe hands those paths to xargs grep -l '"version"', which opens each one and prints only the files that contain a "version" line (-l = "list filenames, not the matching text"). The result is your worklist.

In each listed file, change the "version" value to the new version — format 19.0.1.1.4, no v prefix. When you're done, tell the reviewer how many files you updated, so they can sanity-check nothing was missed.

Why bump them all at once?

Odoo treats each module's version independently — it upgrades a module only if that module's number increased. If you bumped some manifests and forgot others, half the repo would upgrade and half wouldn't, leaving a customer on a mismatched, half-updated install that's very hard to diagnose. Keeping every module on the same version is a deliberate convention that makes "which release is this system on?" answerable at a glance.

💡

Some files may already be on the new number — a fix commit sometimes bumps a single module ahead of the pack (in our example, much_order_shopware_product_import was already at 19.0.1.1.4). That's expected; just bring the remaining modules in line so all of them match. Bumping the ones already there is a harmless no-op.

⚠️

Only edit the "version" line. A manifest also holds depends, data, author info and more — don't touch any of that during a release bump. Changing depends here, for instance, would alter what the module installs and belongs in a real feature PR, not a version bump.

6 Commit the bump

Stage only the manifest files and commit with the exact message format.

git add */__manifest__.py
git commit -m "chore[*] update manifest version

Signed-off-by : {name} <{email}>"

git add */__manifest__.py stages only the manifest files — the */ glob matches each module folder. Staging narrowly matters: it guarantees the commit contains the version bump and nothing else, so the history reads cleanly and a reviewer can trust that a "update manifest version" commit really only did that.

Fill in {name} and {email} from your git config — these identify who cut the release:

git config user.name    # → Joaquim Vicente
git config user.email   # → joaquim.vicente@muchconsulting.com

Why this exact format?

  • chore[*] — our commit-prefix convention. chore marks non-feature, non-fix housekeeping (so it's correctly skipped when the release notes are categorized); the [*] scope means "affects all modules," which a version bump does.
  • The blank line then Signed-off-by : trailer records accountability for the release — the same convention used across our repos, so history stays uniform and greppable.
✍️

Keep the subject line exactly chore[*] update manifest version. Consistency here is what lets us later filter release commits out of changelogs automatically — a one-word difference breaks that.

7 Push the QA branch

The first of three pushes. Get the bump onto GitHub before you start moving code around.

🛑

Ask for confirmation first. A push writes to origin, where teammates and CI will immediately see it — that's why every push in this guide waits for a clear "yes."

git push origin 19.latest-qa

Why push QA first, before merging? The next step fast-forwards Stable to match QA. If QA on GitHub is behind your local copy, that merge would push commits to Stable that don't yet exist on the QA branch remotely — leaving the two branches inconsistent for anyone who pulls. Publishing QA first guarantees GitHub's QA and Stable end up pointing at the exact same, already-visible commit.

A successful push prints the moved range, e.g. d44bb37..9794277  19.latest-qa -> 19.latest-qa — that "old..new" hash pair is your confirmation it landed.

8 Merge into Stable

Bring the freshly-bumped QA work onto the production branch customers install from.

git checkout 19.latest
git merge 19.latest-qa -m "Merge branch '19.latest-qa' into 19.latest"

Step by step: git checkout 19.latest switches you onto the Stable branch (so the merge lands there), then git merge 19.latest-qa pulls QA's commits into it.

What "fast-forward" means and why it's good

Because Stable hasn't diverged — nobody commits to Stable directly, it only ever receives releases — QA is simply "Stable plus the new commits." Git can therefore just slide the Stable pointer forward to QA's tip without inventing a merge commit. That's a fast-forward, and you'll see git say Fast-forward in the output. It's the clean, expected result. (If git instead reports a real merge or a conflict, something committed to Stable out-of-band — pause and check with the team before proceeding.)

🛑

Ask for confirmation, then push Stable — this is the moment the release becomes visible to production:

git push origin 19.latest
ℹ️

Why merge into Stable at all? Stable (X.latest) is the branch deployment systems and customers pull from. Code that only lives on QA has been tested but not released; merging is the act that promotes it to "shipped."

9 Create the version branch

Freeze this exact release under a branch named for the version — the permanent record.

Right now you're on Stable, sitting on the exact commit that is the release. Create a branch named exactly as the version from that point, then push it with tracking:

git checkout -b 19.0.1.1.4
# then, only after confirmation:
git push -u origin 19.0.1.1.4

git checkout -b 19.0.1.1.4 creates and switches to the new branch in one go (the -b = "make a new branch here"). It branches off wherever you currently are — which is why we do this while standing on Stable, so the snapshot captures exactly what shipped.

🛑

Confirm before this third and final push too.

Why -u, and why a branch at all?

  • The branch is the immutable, human-named marker of the release. Stable will keep moving with future releases, but 19.0.1.1.4 stays frozen — so months later "check out exactly what we shipped as 19.0.1.1.4" is one command.
  • -u (short for --set-upstream) links your local branch to the new remote one, so a later bare git push or git pull knows where to go without you re-typing the remote and branch. It's a one-time convenience set at creation.
⚠️

The workflow stops at the version branch — it does not create a git tag unless you're explicitly asked to. (Tagging is sometimes done separately as part of publishing.) Don't invent a v19.0.1.1.4 tag on your own; if the reviewer wants one, ask and do it deliberately.

🔀

Exception — these products skip the version branch. For MCP server, Odoo AI automated Actions, Paypall and Procuro, do not create a version branch as described above. After running /release (e.g. /release 19), instead of branching for this version, simply merge latest into main — e.g. git checkout main then git merge latest. (instead of creating a new branche for this Version, just merge latest into main!)

10 Write the release notes

Two files: one technical for GitHub, one friendly for end users. Read the diffs — don't just copy commit subjects.

Gather the data first

  • Today's date as DD Mon YYYY (e.g. 13 Jul 2026).
  • Contributors (deduplicated, each prefixed with @):
gh api repos/{OWNER}/{REPO}/compare/{LAST_TAG}...{VERSION_BRANCH} \
  --jq '.commits[].author.login'
  • Full changelog URL: .../compare/{LAST_TAG}...v{NEW_VERSION}
  • Read the actual diff of each commit and write a real, human description — git show {hash} --stat then git show {hash}. Include the PR number if the message has one (e.g. #97).
  • Check for new dependencies: look at depends in __manifest__.py diffs and any requirements.txt change.

Categorize each non-chore, non-merge commit

Commit starts with…Goes under
fix…Fixes
feat…New Features
break… / contains BREAKINGBreaking Changes

File 1 — RELEASE_NOTES_v{NEW_VERSION}.md (technical)

Follow the skill's exact template, in this order: Breaking Changes · New Features · Fixes · Deprecated Features · Contributors · full changelog link · Installation/Upgrade instructions · Feedback and support. Support address for these notes: product@erp.muchconsulting.de.

File 2 — USER_RELEASE_NOTES_v{NEW_VERSION}.md (user-friendly)

Same facts, written for end users — plain language, no developer jargon. Use the emoji sections: New Features :tada:, Improvements :microscope:, Bug Fixes :hammer: (each fix described in user terms, referencing its PR number). Feedback address here is different: product@muchconsulting.de.

📧

Two different emails! Technical notes → product@erp.muchconsulting.de. User notes → product@muchconsulting.de. Easy to mix up.

11 Wrap up & cheat-sheet

Tell the reviewer what happened, and keep this table handy.

Final message to the reviewer

  • The release is complete.
  • List the two generated files.
  • Remind them which branch they're on (the version branch).
  • Open both files so they can review them.
