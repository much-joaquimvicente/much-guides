Updating a submodule

Run these in the VS Code integrated terminal (Terminal → New Terminal). A beginner-friendly walkthrough.

What's a submodule? Our main project (product-odoo-19-tests) doesn't contain the module code directly — it contains links to other repositories called submodules (e.g. much-order-base-integration). Each link is a bookmark pointing at one exact version (commit) of that module. Updating a submodule is a two-step dance: update the module, then update the bookmark.
🧠 The big takeaway
Updating a submodule is a two-step dance: (1) Go inside the submodule and git pull to get its latest code. (2) Go back to the main project and git add + commit + push to save which version of the submodule the main project should use.
If you skip step 2, teammates pulling the main project won't get the submodule update — they'll still be pointing at the old version!

Before testing: pull the docs into each environment

Do this once per testing-environment version, before you run any test.

Why this step matters. A freshly cloned version folder only holds bookmarks to the product submodules — not their actual code or documentation. Until you initialise them, those folders sit empty. Pulling the submodules in is what gives each testing environment the proper product documentation to test against.

For each testing-environment version, open its main folder and initialise the submodules once:

$git submodule update --init

This checks out every submodule the version links to and downloads its content — bringing in each product's code and documentation. Once it finishes, the environment has everything it needs and you're ready to test. Tip: add --recursive if a product has submodules of its own.
